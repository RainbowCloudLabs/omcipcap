# OMCIPcap AI Diagnosis CLI Specification

**Status:** Draft (Design Review)

---

## Purpose

The goal of the AI Diagnosis module is to combine existing `omcipcap`
analysis results with Large Language Models (LLMs) to assist engineers
during OMCI troubleshooting.

The first implementation focuses on **prompt construction** and
**provider abstraction**.

`omcipcap` remains responsible for protocol analysis.

The LLM is responsible for reasoning.

---

## Design Principles

The AI layer **MUST NOT** duplicate OMCI protocol parsing.

Instead, it consumes structured Markdown generated by existing
`omcipcap` commands.

Responsibilities:

```
PCAP
    │
    ▼
omcipcap
    │
    ├── check
    ├── mibdb
    ├── vlan-tbl
    ├── tcont-flow
    ├── topology
    ├── overview
    └── diff
    │
    ▼
Markdown Context
    │
    ▼
LLM
    │
    ▼
Diagnosis
```

## AI Providers

The first version supports:

- openai
- claude
- gemini
- openrouter
- ollama

Provider implementations MUST:

- use `requests`
- avoid official SDK packages
- be implemented independently
- expose a unified interface

Provider adapters must be reusable by all AI CLI commands.

### Provider Implementation Requirements

Provider adapters MUST follow the provider's official REST API documentation.

Implementation requirements:

- Use the provider's official REST API.
- Follow the official `curl` examples published by the provider whenever possible.
- Implement HTTP requests using the Python `requests` package only.
- Do NOT use official Python SDKs (for example `openai`, `anthropic`, `google-genai`).
- Keep the implementation lightweight with minimal dependencies.
- Reuse a single `requests.Session` when appropriate.

Each provider adapter is responsible for:

- endpoint URL
- authentication
- request payload
- response parsing
- error handling


### AI Provider Architecture

Suggested layout:

```
omci/ai/providers/
  __init__.py
  base.py
  factory.py
  errors.py
  openai.py
  claude.py
  gemini.py
  openrouter.py
  ollama.py
```

Provider-specific logic MUST NOT leak into CLI code.

### Common Provider Interface

`base.py` MUST define the common provider interface used by all provider adapters.

The interface MUST provide:

- list available models
- send diagnosis requests
- stream generated responses

All providers MUST implement the same interface.

The CLI MUST communicate only with this interface.

Provider-specific response objects MUST NOT be exposed outside the provider layer.

### Provider Factory

`factory.py` MUST expose a single factory function for creating provider adapters.

The CLI MUST create providers through the factory.

The CLI MUST NOT import provider implementations directly.


### Provider Errors

`errors.py` MUST define common provider exceptions.

Provider adapters MUST convert provider-specific HTTP and parsing errors into
shared provider exceptions.

The CLI MUST NOT depend on provider-specific exceptions.


### Authentication

Provider adapters MUST obtain credentials from environment variables.

The CLI MUST NOT accept API keys through command-line arguments.

Provider adapters MUST validate required credentials before making any HTTP request.

### Streaming Requirements

The first implementation MUST support streaming responses for both:

- `omcipcap ai diag`
- `omcipcap ai diag-diff`

Provider adapters MUST follow each provider's official streaming REST API and
implement it using `requests` with `stream=True`.

Official provider SDKs MUST NOT be used.

Provider-specific streaming events MUST be normalized into plain text fragments
before being returned to the CLI.

The CLI MUST:

- write generated text incrementally to stdout
- flush stdout after every fragment
- preserve Markdown formatting
- write warnings, progress, and errors to stderr
- remain compatible with shell redirection
- print a final newline after successful completion
- return a non-zero exit status if the stream fails

If a stream fails after partial output has already been written:

- keep the partial response on stdout
- report the failure on stderr
- return a non-zero exit status

### Model Listing

Provider adapters are responsible for retrieving supported models.

If the provider supports remote model discovery, the adapter SHOULD query the
official API.

Otherwise, the adapter MAY provide a documented built-in model list.

The CLI MUST treat every provider identically.

### Testing

Provider implementations MUST be unit-testable.

Tests MUST mock HTTP requests.

Tests MUST NOT depend on external AI services or Internet connectivity.

## CLI

### List supported providers

```
omcipcap ai providers
```

Returns supported provider adapters.

No API key required.


### List available models

```
omcipcap ai models --provider PROVIDER
```

Examples:

```
omcipcap ai models --provider openai

omcipcap ai models --provider claude

omcipcap ai models --provider openrouter

omcipcap ai models --provider ollama
```

Provider authentication depends on the provider.

### Single PCAP Diagnosis

```
omcipcap ai diag \
    omci.pcap \
    --problem-md problem.md \
    --provider openrouter \
    --model anthropic/claude-opus-4.5
```

Purpose:

Analyze one OMCI capture using AI.

Input:

- target PCAP
- user problem description
- AI provider
- model

Generated context:

```
System Prompt

+

problem.md

+

overview Markdown
```

The exact prompt wording is intentionally left unspecified in this document.

### Golden Case Diagnosis

```
omcipcap ai diag-diff \
    failing.pcap \
    --golden-pcap golden.pcap \
    --problem-md problem.md \
    --provider openrouter \
    --model anthropic/claude-opus-4.5
```

Purpose

Compare a failing capture against a known-good capture.

Recommended assumptions:

- same OLT
- same ONU model
- same service configuration

The AI should determine why the golden capture succeeds while the failing
capture does not.

#### Context Selection

Calculate:

```
difference_count =
    removed_count
    + added_count
    + modified_count
    + unknown_me_mask_mismatch_count
```

##### difference_count <= 5

Context:

- problem.md
- diff Markdown

The assumption is that a small semantic difference set is sufficient for
AI diagnosis.

##### difference_count > 5

Context:

- problem.md
- diff Markdown
- failing overview Markdown
- golden overview Markdown

The larger context helps the AI understand interactions between multiple
semantic differences.

## Privacy

Cloud AI providers receive OMCI analysis data.

Users should remove:

- customer names
- serial numbers
- IP addresses
- credentials
- confidential deployment information

before sending data to cloud providers.

---

## Out of Scope

The first implementation does NOT include:

- prompt optimization
- prompt templates
- conversation history
- automatic retries
- tool calling
- cost estimation
- prompt caching
- automatic redaction
- AI-assisted command execution

These items may be implemented in future releases.
